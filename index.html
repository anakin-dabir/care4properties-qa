Site is stable at time of survey

No Rating 3 defects. Every page returned 200, the property search API answered in 1.86 s, and both listing feeds are healthy. The defects below are quality and visibility issues, not outages.

Rating 2 — defects requiring repair

Reproduced live today. None are breaking the site; each costs reach, safety or usability.

2C1

The valuation widget covers property listing text

/properties · 1440×1150 · floating CTA

The floating “Book a Free Valuation” panel is pinned to the bottom-right of the viewport and sits on top of the property cards behind it. On the listing page it cuts every description mid-sentence — the reader loses the end of each line and there is no way to read it without dismissing the panel.

  • 1The floating panel, layered above page content.
  • 2Description text truncated behind it — “This propert…”, “offering comfort and conve…”, “leisure facil…”.
Repair

Reserve space for the panel rather than floating it over content — add right padding to the card grid at widths where the panel is shown, or collapse it to the small pill used on mobile. Persist dismissal so it stays closed once shut.

2C2

No sitemap, so listings rely on link discovery alone

GET /sitemap.xml → 404

There are 112 properties across the two feeds, each with its own page, plus blog and news articles. Without a sitemap, search engines have to find all of them by following internal links, and get no signal about which pages changed or when. 

GET /sitemap.xml   404
GET /robots.txt    404
src/app/sitemap.ts  not present
Repair

Add src/app/sitemap.ts. Next.js generates the XML from it, and it can read live property IDs from the feed so new listings appear without a redeploy.

2C3

No robots.txt

GET /robots.txt → 404

Crawlers receive no guidance. /admin-dashboard and transient routes such as /thankYou, /select-viewing-time and /feedback are as open to indexing as the property pages.

Repair

Add src/app/robots.ts — disallow admin and transactional routes, and reference the new sitemap.

2C4

The homepage has no description and no share preview

GET / · document head

Property pages are set up properly — description, Open Graph title, image and summary all present. The homepage carries only a title tag. It is the most linked and most shared URL on the site, and it shares as a bare link with no image or copy. 

homepage
  <title>Home - Care4Properties</title>
  description  absent
  og:*         absent

/properties/rent-1220
  <title>Cross Flatts Place, LS11 7JN — £1350.00 | …</title>
  description  present
  og:title / og:description / og:image   all present
Repair

Export a metadata object from the homepage with a description and Open Graph block, following the pattern already working on property pages.

2C5

Five security headers are absent

Response headers, all routes

HTTPS and HSTS are correctly configured. The rest of the standard set is missing, leaving the site embeddable in a hostile iframe and allowing browsers to guess at content types. 

strict-transport-security   present  (max-age 63072000)
content-security-policy     missing
x-frame-options             missing
x-content-type-options      missing
referrer-policy             missing
permissions-policy          missing
Repair

Add a headers() block to next.config.js. Ship the four simple ones first; introduce CSP in report-only mode so it cannot break the Google Maps embed or Backblaze-hosted property images.

2C6

A malformed property URL hangs instead of returning 404

GET /properties/sale- (empty id)

A property URL with a missing ID never responds. The request was still open when the probe abandoned it at 45 seconds. Anyone following a truncated link — and any crawler that finds one — sits on a blank page until the browser times out, while a server slot stays occupied. 

/properties/rent-1220   200   1.90s
/properties/sale-       no response after 45s
Repair

Validate the ID against (sale|rent)-<digits> before fetching and call notFound() when it does not match. Add a timeout to the upstream feed request so no path can hang indefinitely.

1C8

Listings render a skeleton before data arrives

/properties · client-side fetch

Properties are fetched in the browser after the shell loads, so the page shows “Loading…” and grey placeholders for roughly two seconds before cards appear. The skeleton is well built and the wait is short, but on a slow connection the listing page is empty for noticeably longer. 

filterProperties  →  200 in 1.86s
listing populated with 7 properties
Repair

None required. Worth revisiting only if listing pages become a ranking priority, since the property data is invisible to crawlers that do not execute JavaScript.

1C9

Server response times run 1.4 to 3.9 seconds

Time to first byte, 8 routes

Google treats anything beyond 0.8 s as needing improvement. Nothing here is slow enough to hurt usability, but the two content pages are roughly four times that guideline.

/properties/rent-1220                1.90s

Repair

Measured from a single location, so treat as indicative. If it becomes a priority, the two slow routes are worth profiling first — both are content pages that should be cheap to serve.
